## Overview

EUR-Lex MCP server wraps the **CELLAR** semantic repository operated by the EU Publications Office — the authoritative, machine-readable database of European Union law covering 2.7M+ works: treaties, regulations, directives, decisions, CJEU/General Court judgments, Advocate General opinions, and preparatory acts.

Access paths, both served by the EU Publications Office: the **CELLAR SPARQL endpoint** (`http://publications.europa.eu/webapi/rdf/sparql`) for metadata and relationship graph queries, and **CELLAR content negotiation** (`http://publications.europa.eu/resource/celex/{CELEX}`, with `Accept` / `Accept-Language` request headers) for document full text.

Audience: EU and comparative-law practitioners, regulatory and policy analysts, academics, journalists, and AI agents answering "what does EU law say about X", tracing an EU act's lifecycle, or composing EU ↔ US cross-jurisdiction comparisons.

## Requirements

- All queries are read-only; no authenticated or registered-user paths required
- Every SPARQL query MUST include `LIMIT` (max 100) and support `OFFSET` for pagination; Virtuoso enforces a 60-second query timeout
- Document content retrieved via CELLAR content negotiation (`GET /resource/celex/{CELEX}` with `Accept` + `Accept-Language`), the same Publications Office host as the SPARQL metadata path; the legacy `eur-lex.europa.eu/legal-content` endpoint is now behind an AWS WAF bot-challenge and no longer serves act text (issue #16)
- CELEX number is the primary document identifier; ELI URIs are the secondary
- Multilingual corpus: default to English (`EN`), expose a `language` parameter; some older acts lack EN translations
- Keyless: no API key, no registration required; both endpoints are publicly accessible
- Relationship graph is the server's primary value differentiator — `eurlex_get_relations` must traverse `cdm:work_cites_work`, amendments, consolidations, and legal basis
- EuroVoc concept IDs are required for subject-filtered searches; `eurlex_browse_subjects` is the prerequisite tool
- Keyword search matches English expression titles through Virtuoso's `bif:contains` full-text phrase index (multi-word input is quoted as a single phrase), with a CELEX arm chosen by the keyword's shape: a whole CELEX matches its bounded family of exact literals (itself, `(01)`–`(20)`, `R(01)`–`R(20)`, and the `_INF`/`_RES`/`_SUM`/`_EXT` records) plus its linked corrigenda, a partial CELEX through prefix terms on the CELEX full-text index with a confirming substring test, an OJ C fragment such as `2024/01469` on its number word (one opening with letters no digit follows, such as `R(01)`, or with a year, a slash, and a number shorter than four characters, such as `2017/111`, by a substring scan of every CELEX literal; a bare year or a fragment opening mid-year or mid-number matches titles only), and a keyword with no digit or with a character no CELEX holds matches titles only; a keyword with no letter or digit is rejected as `invalid_keyword`; there is no full-text search of act body text
- `eurlex_query_sparql` is an escape hatch; LIMIT is injected or capped at 100 by the service layer — if the input query omits LIMIT or sets it above 100, the service rewrites it before executing

## Services

| Service | Wraps | Used By |
|:--------|:------|:--------|
| `CellarSparqlService` | CELLAR SPARQL endpoint (`publications.europa.eu/webapi/rdf/sparql`) | All tools except `eurlex_get_document` text fetch |
| `EurLexContentService` | CELLAR content-negotiation resolver (`publications.europa.eu/resource/celex/...`) | `eurlex_get_document`, `eurlex_lookup_celex` (metadata enrichment) |

Both services are HTTP-only, no auth. `CellarSparqlService` POSTs `application/x-www-form-urlencoded` with `Accept: application/sparql-results+json`. `EurLexContentService` GETs `/resource/celex/{CELEX}` under content negotiation — `Accept: application/xhtml+xml` / `text/html` for HTML, `application/xml;type=fmx4` for Formex 4, then `application/zip;mtype=fmx4` when that variant answers 404 (#108) — with an `Accept-Language` ISO 639-2/T code. `EurLexContentService` also caches each available body it serves in process, keyed by CELEX, requested language, and format, and holds Markdown with its heading list rather than the HTML behind it (#127, #129).

## Implementation Order

1. **Config** — `src/config/server-config.ts` with Zod schema for the four env vars above
2. **`CellarSparqlService`** — SPARQL POST client, result-binding mapper (`binding.value` extraction), LIMIT enforcement, retry on transient 5xx; CDM PREFIX declarations built in
3. **`EurLexContentService`** — content-negotiation GET client for `/resource/celex/{CELEX}`; handles language fallback when EN is unavailable
4. **`eurlex_lookup_celex`** — the foundational tool; validates CELEX/ELI/ECLI input and parses OJ citations, resolves to work URI + confirmed CELEX
5. **`eurlex_browse_subjects`** — EuroVoc thesaurus search via SPARQL; prerequisite for subject-filtered workflows
6. **`eurlex_search_documents`** — parameterized SPARQL builder; keyword, type, date, EuroVoc, in-force filters
7. **`eurlex_get_cases`** — case law variant of search; CELEX sector 6 filter, court/case-type parameters
8. **`eurlex_get_document`** — metadata via SPARQL + content text via `EurLexContentService`; assembles full response
9. **`eurlex_get_relations`** — CDM relationship traversal; deduplicated relation type output
10. **`eurlex_query_sparql`** — escape hatch; server-side LIMIT injection if missing from input
11. **Resources** — `eurlex://document/{celexNumber}` and `.../relations`
12. **Prompt** — `eurlex_comparative_analysis`

## Workflow Analysis

### `eurlex_get_document` (2 upstream calls)

| # | Call | Service | Purpose |
|:--|:-----|:--------|:--------|
| 1 | SPARQL: resolve the CELEX to its work and, concurrently, locate it among its act's consolidated versions; then read the metadata (core fields, agents, legal bases, EuroVoc concepts in parallel) | `CellarSparqlService` | Title, date, type, a case's ECLI, author institutions, Advocates General, legal bases, EuroVoc concepts, in-force flag and the reason an act is not in force, base act, current consolidated version |
| 2 | GET `/resource/celex/{celex}` with `Accept: text/html` (or `application/xhtml+xml`) + `Accept-Language` | `EurLexContentService` | Full HTML text of the act in requested language |

If step 2 cannot resolve usable content for the requested language, retry with `EN`. A successful fallback records both requested and effective language. If both attempts fail ordinarily, return metadata with `content_status: "unavailable"` and a typed cause (`no_representation`, `upstream_failure`, or `multipart_incomplete`); the text channel closes with a line keyed on that cause, and only `no_representation` names the language (#108). A zipped Formex package that cannot be read or assembled is `multipart_incomplete`, like an incomplete 300 assembly. A WAF challenge on the primary representation remains a hard `content_challenge` error; sibling-part challenge failures during multipart assembly remain best-effort unavailability.

The exact shaped `content` string is shared by `structuredContent` and the formatter. HTML and XML are presented literally in `content[]` inside a dynamically safe tilde fence longer than any tilde run in the source; Markdown remains rendered Markdown. Every body returned in one call contains at most 100,000 characters. For the contiguous modes — offset-based `paged` and `full` — clients reconstruct larger bodies through sequential `paged` calls using the returned offsets and total. A `select` response is bounded the same way but is not a contiguous window: it is a set of disjoint slices, so `has_more` stays false (its `offset = content_offset + content_chars_returned` recipe cannot resume across them), `content_offset` is absent, and a cut is disclosed through the `truncated` enrichment. `selected_sections` carries each matched section's own `offset` and `chars`, which is both the navigation the response actually has and the address that keeps every section individually reachable through the paging floor. `outline` returns no body text, so its bound is vacuous; it reports `content_chars_returned: 0` and renders a structure line rather than a character range.

> **Consolidated versions follow the based-on link (#109, #110).** Every CELEX-bearing consolidated text carries exactly one `cdm:act_consolidated_based_on_resource_legal` link to its base act and one `cdm:act_consolidated_date`, and its CELEX is in sector `0` (33,126 of them on 2026-09-25). One lookup, keyed on the typed CELEX and run concurrently with CELEX resolution, reads an act's newest consolidation — the latest date on or before today, so a consolidation dated in the future never counts, and ordered by date rather than CELEX because one act's consolidations can be numbered differently (`32000O0007` → `02000X0776-…` and `02000O0007-…`). For a consolidated CELEX the same query also returns its own date and its base act's work and CELEX; a base act's request replaces the old staleness probe, so neither path adds a serial round trip. The former `…consolidates…` edge plus a `0{act}-YYYYMMDD` CELEX match missed 968 consolidations of 443 acts and also reaches amending acts. `is_superseded` describes the text served: `false` on the newest version and on a consolidated version dated after it (which does not apply yet), `true` otherwise, present whenever the act has a consolidated version in effect; the field name stays, since #49 ruled it is not a repeal signal. With no version in effect there is nothing to be stale against, yet a future-dated text must not read as applicable: a consolidated text dated after today with no version in effect (`02021D1442-20261001`) carries a `notice` that it does not apply yet, and a base act's lookup also reads one future-dated consolidation in an OPTIONAL arm of the same query, so `resolve: "current_consolidated"` on an act with only such versions (`32021D1442`) serves the base act with a `notice` naming the pending version. A consolidated text records its act's metadata nowhere — 59,668 name the Publications Office's provisional-data code as author, none carries an in-force flag, subjects, or a legal basis — so `eurlex_get_document` and `eurlex://document` read those from the linked base act and name it in `base_act_celex`; the base CELEX is not derivable from the consolidated one (`02003T0000-20040501` → `12003T/TXT`). A consolidated text with no link, or whose base carries no CELEX, reads its own metadata.

> **An act not in force names why (#111).** Of 82,203 works CELLAR marks not in force (2026-09-25), 13,400 are the target of an explicit repeal, 59,279 have a past end of validity and no repeal edge, and 56 have an earliest entry into force still ahead. `eurlex_get_document` reads all three in the core metadata query as aggregates — `MIN(STR())` of `cdm:resource_legal_date_entry-into-force`, `MAX(STR())` of `cdm:resource_legal_date_end-of-validity`, and a `GROUP_CONCAT` of the CELEX of every work whose `cdm:resource_legal_repeals_resource_legal` names the act — so no query is added; `STR()` sidesteps CELLAR's wrong grouped `MAX` over an `OPTIONAL` `xsd:date`. They are reported only when `in_force` is false, since 334 acts in force are the target of a partial repeal: `repealed_by` (the explicit relation; implicit repeals stay with `eurlex_get_relations`), `entry_into_force` only when after today (UTC), and `end_of_validity` except CELLAR's open-ended `9999-12-31`. That placeholder is filtered inside the end-of-validity `OPTIONAL`, not after the aggregate: 249 acts not in force carry several end dates, and two (`32000D0670`, `32020D1531`) record a real one beside `9999-12-31`, which a `MAX` over both would hide. An end of validity is not always past — an act not yet in force can already carry one ahead (`32026R1975`: in force from 2026-09-29, valid until 2030-12-31). Not every act not in force carries a reason: 1,527 with a CELEX record none of the three. A consolidated text reports its base act's.

> **A work_uri carrying several CELEX serves the lowest (#104).** 19,024 works carry more than one CELEX, up to 347 each, all national implementing measures (sector 7) holding one per directive they were notified against; each is an `owl:sameAs` alias of the same work, so none is canonical. The dereference reads `MIN(STR())` and the count in one query, the order `eurlex_get_relations` reads a work's CELEX in, and a `notice` names the count and the CELEX served. Failing the call was rejected — every CELEX names the same document — as was returning every CELEX, up to 347 per call.

> **Nested selections carry each source character once (#88).** A section ends at the next heading of the same or broader rank, so two selected spans are always nested or disjoint, never partially overlapping. `content` is built from the outermost spans only: an article selected alongside the chapter holding it adds no slice and no characters to the cap, and the `truncated` notice's pre-cap total counts each character once. Adjacent sections stay separate slices. The nested section keeps its own `selected_sections` entry, and `selection.matched` is unchanged; the text rendering counts the slices `content` carries and names how many nested sections ride inside them.

### `eurlex_get_relations` (1 SPARQL call, potentially 2)

| # | Call | Purpose |
|:--|:-----|:--------|
| 1 | SPARQL UNION: all `?work ?rel ?target` and `?source ?rel ?work` where rel in CDM relation set | Get all incoming and outgoing CDM relations |
| 2 | SPARQL: resolve CELEX numbers for related work URIs (if not in first result) | Enrich relation targets with CELEX for human-readable output |

CDM relation predicates to traverse (as built — see `RELATION_SPECS` in `relation-traversal.ts`; CELLAR models amendment and consolidation one-directionally, so the "reverse" types are the incoming side of the forward predicate, and the dedicated `…amended_by…`/`…has_consolidated_version…` predicates carry zero triples):
- `cdm:work_cites_work` — citation graph (both directions)
- `cdm:resource_legal_amends_resource_legal` — `amends` (outgoing) and `amended_by` (incoming)
- `cdm:resource_legal_repeals_resource_legal` — `repeals`/`repealed_by`; `…implicitly_repeals…` likewise for the implicit pair
- `cdm:resource_legal_based_on_resource_legal` — legal basis
- `cdm:act_consolidated_based_on_resource_legal` — `consolidated_version` (incoming: each consolidated text points back to its one base act)

## Design Decisions

**Tool split: `eurlex_search_documents` vs `eurlex_get_cases`**
Case law is a distinct sub-audience (litigation practitioners, academics, agents tracking precedent) with different search parameters (case number, court, party, AG opinion type). Merging into one tool with a `document_type` filter buries the case-law-specific parameters. The split mirrors how EUR-Lex itself separates legislation from case law browsing.

**No full-text search across document body text**
CELLAR SPARQL search is metadata-and-title only; full-text search of act body text is not available via the public SPARQL endpoint. The `keyword` parameter on `eurlex_search_documents` and `eurlex_get_cases` matches English expression titles through Virtuoso's `bif:contains` full-text index (multi-word input quoted as a phrase) and CELEX numbers — by exact lookup for a whole CELEX and its bounded sibling family, through the CELEX full-text index for a partial one, by a substring scan of every CELEX literal for a fragment opening with letters no digit follows or with a year, a slash, and a number shorter than four characters, not at all for a keyword with no digit, a bare year, or a fragment opening mid-year or mid-number — never the act body. This is a real limitation — document the constraint clearly in tool descriptions.

**Content via CELLAR content negotiation, not EUR-Lex REST (issue #16)**
The `eur-lex.europa.eu/legal-content` endpoint is now fronted by an AWS WAF that returns a JavaScript bot-challenge stub instead of act text, so content is fetched from the CELLAR resolver at `http://publications.europa.eu/resource/celex/{CELEX}` — the same Publications Office host as the SPARQL metadata path — by content negotiation. `Accept` selects the representation (OJ legislation exposes `application/xhtml+xml`, CJEU judgments expose `text/html`, so the HTML path tries both; Formex 4 uses `application/xml;type=fmx4`) and `Accept-Language` carries an ISO 639-2/T code. Multi-part OJ acts return HTTP 300 (Multiple Choices) and are reassembled from their sibling Formex streams. Some acts CELLAR holds only as a zipped Formex package: their `fmx4` variant answers 404, and `application/zip;mtype=fmx4` returns the package (#108; in a sample of eight, every act from `32022R2065`, October 2022, on was zip-only, and every earlier one answered 300, but the split is not by date: `32019R0876` is zip-only too). The package is requested only after that 404, so acts that answer 200 or 300 cost no extra request. Its `<DOC>` manifest (`*.doc.fmx.xml`, or `*.doc.xml` in older packages) and each file its `<REF.PHYS FILE>` elements name are assembled, in manifest order, into the same `<formex-multipart>` wrapper as the 300 path, with a comment naming the source; entry order is not used (`32023R2854` stores the act before the manifest), and the OJ-issue table of contents, which no `REF.PHYS` names, is left out. The archive is read by a small central-directory reader over `node:zlib` `inflateRawSync` (`formex-package.ts`), which runs unchanged on Bun and Node, rather than a dependency or the Bun-only `Bun.Archive`. It is untrusted input: declared sizes are capped at 32 MiB in all, each entry inflates only up to its declared size and must match it exactly, and traversal or duplicate names, encrypted entries, and unsupported methods reject the package. A package that does not read or names a missing part is `multipart_incomplete`, never a throw; a WAF challenge answering the package request is refused like any primary one. HTML is the primary format; Markdown is rendered server-side from it. Any response carrying a WAF challenge signature is refused and raised as `ServiceUnavailable`, never surfaced as content.

**`eurlex_query_sparql` as escape hatch (included)**
CELLAR's CDM ontology has ~200+ predicates; the curated tools cover the 80% case. A raw SPARQL tool is warranted given the wikidata-server precedent and CELLAR's depth. Server-side LIMIT injection (cap to 100) prevents timeout abuse. The tool earns its keep.

**The raw SPARQL tool names the untyped-literal trap and never rewrites the query (#115)**
Read-only ASK, CONSTRUCT, and DESCRIBE queries, a misspelled keyword, and a prologue with no query fail as `unsupported_query_form`; `not_read_only` is kept for the ten SPARQL 1.1 Update keywords, so the reason says what the caller sent. A plain string literal as a triple object matches nothing in CELLAR, which types CELEX, ECLI, and `cdm:work_id_document` as `xsd:string` and ELI as `xsd:anyURI`. The query is still forwarded byte for byte: the right datatype depends on the predicate, a safe rewrite needs a full SPARQL parser, and silently changing what the escape hatch runs was rejected. A zero-row result instead carries a `notice` naming the literal and the typed forms. The detector skips comments, IRIs, and literal contents, ignores literals inside parentheses (`FILTER(LANG(?l) = "en")` is legitimate), `bif:contains` phrases, and `VALUES` data; `FILTER(?c = "…")` shares the trap and is covered by the `sparql_query` guidance, not the notice. In result tables a `_` between two letters or digits stays bare, since CommonMark never lets it open or close emphasis there; every other character #76 escapes is still escaped.

**EuroVoc matches rank in tiers inside the query (#113)**
`eurlex_browse_subjects` orders concepts by the best tier any of their labels reaches in the requested language — exact preferred or alternative label, then a label or a word in it starting with the keyword, then any other substring — and by preferred label, then concept URI, within a tier. The tier is a `MIN(IF(…))` aggregate in the SPARQL `ORDER BY`, ahead of `LIMIT`/`OFFSET`: CELLAR cuts the page, so re-sorting a returned page could never lift "AI" (concept 3030, 125th of 399 alphabetically) onto page 1. Plain `STRSTARTS`/`CONTAINS(label, " keyword")` tests replace a `REGEX` whole-word test, which made the `"ai"` query several times slower; the default `"ai"` page answered in 4 s on a single live draw (2026-09-25), inside the 55 s client timeout. A subselect variant lost the label order within a tier. `matched_label` is the MIN of a tier digit plus the alternative label, so it reports the best-tier alternative, alphabetical among equals, where `SAMPLE` could return a weaker one. The output shape is unchanged.

**EuroVoc predicate is `cdm:work_is_about_concept_eurovoc`**
Not `cdm:work_is_about_subject_matter` (that's a separate EU subject-matter authority) and not `cdm:work_is_about_subject` (the correct name is `work_is_about_concept_eurovoc`). Confirmed by inspecting GDPR's predicate set via SPARQL. The wrong predicate was in the idea doc sketch — this was caught by live API probing.

**Title keyword search via the `bif:contains` full-text index (issue #17)**
The title match runs through Virtuoso's `bif:contains` full-text index rather than a `FILTER(CONTAINS(LCASE(?title), …))` scan: the scan forced the expression graph to be joined for every candidate work before the term was tested, so a broad keyword timed out. Multi-word input is quoted as a single phrase (`bif:contains "'data protection'"`), and the input is sanitised to letters, digits, and spaces so it cannot break out of the phrase. The CELEX arm is a UNION arm chosen from the uppercased keyword (#105), shared by both search tools: none when the keyword has no digit or a character outside `[0-9A-Z()/_-]` (a digit-free keyword could only hit type letters across every CELEX literal, and `privacy` went from 43 s to 0.7 s with identical rows); exact typed literals `"…"^^xsd:string` when a work carries the keyword as its whole CELEX (`32016R0679` went from 29 s to 0.5 s); otherwise the partial arm below (#123), so `2016R0679` still reaches `02016R0679-20160504`. Whether the keyword is whole is decided by a lookup rather than by pattern, since `02016R0679` and `72014L0056` are CELEX-shaped prefixes no work carries. That one lookup joins a `VALUES` list of the keyword's bounded family — itself, the numbered siblings `(01)`–`(20)`, the corrigenda `R(01)`–`R(20)`, and the `_INF`, `_RES`, `_SUM`, and `_EXT` records of the CELEX and of each numbered sibling, 125 literals — and returns the members CELLAR carries; when the keyword itself is among them, the search joins those members as a `VALUES` list, plus the works whose `cdm:resource_legal_corrects_resource_legal` points at the CELEX. The family keeps the recall the substring scan gave a whole CELEX (`62023CO0097` reaches its `(01)` and `(02)` orders, `32016R0679` its `R(01)`–`R(03)`) without scanning. The vocabulary and the bound come from a live survey of every CELEX (2026-09-25): past the base, sector 6 carries `(nn)` up to `(20)`, `_INF`, `_SUM`, `_RES`, `_EXT`, those four on a numbered sibling, and `R(01)`; sector 3 carries `R(nn)` up to `R(30)` and `(nn)` up to `(61)`, with under 1% of corrigenda and 8% of numbered siblings past 20. Longer forms, a corrigendum of a numbered sibling, and sector-3 `P…` parts stay out of the family. The 125-literal lookup ran in 0.37–0.58 s, and the widened search arm matched the plain exact arm (0.29–0.39 s against 0.29–0.31 s). `eurlex_get_cases` still admits the notice, abstract, and summary records only under `include_derivative`, through the derivative-type filter every row passes; an `_EXT` extract is typed `JUDG_EXTRACT`, a primary record. A keyword with no letter or digit can match no title and no CELEX, so both tools reject it as `invalid_keyword` before any CELLAR call rather than answer it with an empty page that drops every other filter. (The EuroVoc label search in `eurlex_browse_subjects` is a different path and still uses `FILTER(CONTAINS(LCASE(?label), …))`.)

**A partial CELEX keyword narrows through the CELEX full-text index (#123)**
The partial arm was `FILTER(CONTAINS(LCASE(STR(?kwCelex)), …))`, a test of every CELEX literal, so `R0679` passed the 55 s client timeout and `2016R0679` answered only after the scan. CELLAR full-text-indexes CELEX literals, so the arm now binds `?kwCelex bif:contains "'02016R0679*' OR … OR 'E2016R0679*'"` and confirms with `FILTER(CONTAINS(STR(?kwCelex), K))` on the uppercased keyword. The index does not split a word between digits and letters (`'2016R0679*'` alone matches nothing), so each term completes the keyword's leading `[0-9A-Z]` run to the start of a CELEX, `{sector}{year}{type code}`, a year being 1951 through next year (no CELEX carries a sector and year before 1951). `celexFragmentRoute` reads the run:

- five digits (`02016R0679`): its own term, a sector digit and a year; the index splits words at `-`, so `20160504` also reaches the consolidations of that date;
- `C` or `E` and a year (`C2006`, `E2003C0097`): its own term plus the type-letter reading below, since `51973PC2017` and `52009AE1952` hold `C2017` and `E1952` as type letters and number;
- a year and a letter (`2016R0679`): behind each of the 12 sector characters;
- a year and a slash, alone or behind `C/` (`2024/01469`, `C/2024/0146`): the number word after the slash as its own term (#137, below); the substring scan when that word is shorter than four characters (`2017/111`);
- letters followed by a digit (`R0679`, `CJ0362`, `J0131`, `C0097`): behind every sector, year, and type code ending in those letters, so `J0131` reaches `62013CJ0131` (616 terms in 2026), from `CELEX_TYPE_CODES`, a per-sector table of the 232 type codes CELLAR carried on 2026-09-25, pinned by a test; letters no type code ends in keep the substring scan;
- letters no digit follows (`R(01)`, `ROU_202405`): the substring scan of every CELEX literal, `FILTER(CONTAINS(STR(?kwCelex), K))`, since those letters can sit anywhere after the type code;
- anything else, including four digits before a letter that are no year and a bare year (`016R0679`, `0679`, `0679R`, `0680DEU`, `9999R0679`, `2016`): no CELEX arm, titles only, a recall change for fragments opening mid-number.

The index also splits words at `-`, `_`, and `/`, so a term can hit a consolidation date or a suffix, and the confirming `FILTER` is required rather than optional. Every term is built from that validated run plus sector characters, digits, and the table's type codes, so no caller text can close the phrase or add an operator; the confirming and scanning literal is the keyword already restricted to CELEX characters. Two shapes are not reached, and read as a year or a type code instead: a number that reads as a year followed by letters (`1998R` in a `…R1998R(01)` corrigendum), and a letter run after the number (`P1331` in `31962D0241P1331`, about 430 CELEX in sectors 1 and 3). Reading any `C` or `E` and four digits as a sector and year, and putting a bare letter run behind every sector and year, was rejected: live it lost every row for `C0097`, `C0123`, `E0124`, `J0131`, and `N0123`, 7 of 89 for `R0065`, and expanded `R(01)` into 924 terms that timed out. With the type-code table, the arm matched the substring scan's CELEX set exactly (2026-09-25): `C0097` 92, `C0123` 160, `E0124` 259, `J0131` 59, `N0123` 41, `R0065` 89, `C2017` 927, `E1952` 1, `R0679` 65, `CJ0362` 21, each in 0.3–4.2 s; the scan answered `R(01)` (18,295) in 11–58 s and `C/2024/0146` (5) and `ROU_202405` (15) in 5 s. Earlier checks of the year-and-letter class matched `2016R0679` (5), `2016L0680` (338, 333 of them sector-7 national measures), and `2026R19` (29); the full tool queries returned identical rows, order, and fields: `R0679` in 0.6 s (past the timeout before), `2016R0679` in 0.3 s, `eurlex_get_cases` `2014CJ0362` in 0.4 s, and a `date_from` search on `2016R0679` in 0.5 s against 52 s. A typed-literal range comparison returned wrong rows on CELLAR, `STRSTARTS` still scanned, and enumerating whole CELEX values cannot reach the unbounded consolidation and national-measure suffixes, so the index was chosen.

**An OJ C `[C/]{year}/{number}` fragment narrows through the index on its number word (#137)**
CELLAR files OJ C documents under CELEX such as `C/2024/01469` (1,907 on 2026-09-25), plus the older `C2017/111/07`; no other CELEX holds a `/`. A keyword holding one scanned every CELEX literal, and `2024/01469` passed the client timeout. The index splits words at `/`, so every CELEX holding `{year}/{number}` has a word starting with the number: `celexFragmentRoute` takes the `[0-9A-Z]` run after the slash as the one term (`'01469*'`), and the existing `FILTER(CONTAINS(STR(?kwCelex), K))` confirms the whole fragment. A bare `{year}/` still needs a year from 1951 through next year and otherwise matches titles only; behind `C/` any four digits take the route, since the confirming test holds either way. CELLAR rejects a prefix term with fewer than four leading characters (Virtuoso FT370, "Wildcard word needs at least 4 leading characters"), so a shorter number (`2017/111`, `2024/014`) keeps the scan, while `C2017/111` takes the `C`-and-year route on `C2017`. A whole OJ C CELEX a work carries (`C/2024/01469`) still takes the exact family arm. Live (2026-09-25), the generated `eurlex_search_documents` queries returned identical rows, order, and fields to the scan: `2024/01469` 0.5 s against 17.5 s, and `C/2024/0146` (5 rows) 3.8 s against 29.8 s; `2024/014`, which keeps the scan, took 52.7 s for 17 rows. Terms are built from the validated run alone, and a test pins every term at four characters or more.

**A parsed case_number narrows through the CELEX index, its REGEX confirming (#138)**
A parsed case number filtered with the unanchored `FILTER(REGEX(STR(?celexNumber), "{year}{court}[{document letters}]{number}"))`, which tests every sector-6 CELEX literal; `C-443/14` and `82/85` passed the client timeout under load. The match now puts one prefix term per admitted document letter in front of that `REGEX` (`?celexNumber bif:contains "'62014CJ0443*' OR '62014CO0443*' OR …"`), from `CASE_NUMBER_DOCUMENT_LETTERS` for the court, with the notice letters only when `include_derivative` admits them and no `case_type` is set. The terms reach every CELEX the `REGEX` admits: by the #134 survey a four-digit year followed by two letters sits only at position 2 of a sector-6 CELEX, so a match always opens the literal's first word, which the term prefixes whatever follows: siblings (`61985CO0082(01)`), corrigenda (`62017TN0161R(01)`), suffixed records (`62021CO0121_1`), and a five-digit number (`62014CN00016` for `C-1/14`) stay reached. A year written with fewer than four digits (`C-131/012`, read as 12) keeps the `REGEX` alone, since it matches those digits at the end of a four-digit year. Each term comes from the parsed digits, the court letter, and the letter table, never from caller text; a test drives payloads and random text after the year and pins the expression. Live (2026-09-25), rows, order, and fields matched the `REGEX` query: `C-443/14` 0.3 s against 4.8 s, `82/85` 0.3 s against 8.4 s, and `C-131/12` with `include_derivative` (4 rows, notices included) 0.3 s against 24.6 s; the only difference, in `C-443/14`, was the `SAMPLE(?work)` pick for a CELEX several works hold, which the row's canonical-work resolution (#97) replaces.

**A case_number that parses as no case number narrows through the CELEX index when its opening allows (#134)**
The fallback scanned every CELEX literal with `FILTER(CONTAINS(LCASE(STR(?celexNumber)), …))`. A value that opens with the sector and year (`62014CJ0362`), the year and both letters (`2013CJ0131`), or both letters and the number (`CJ0131`) now takes the keyword's partial arm on `?celexNumber` (the `celexFragmentRoute` terms kept to sector 6, via `celexPrefixMatch`); every other value keeps the scan byte for byte, as does an indexed opening the route gives no sector-6 term (a year past next year, `QQ0131`, or `XC0131`, whose letters only other sectors' codes end in), which no sector-6 CELEX holds. The gate holds because a live check of every sector-6 CELEX (2026-09-25) found them upper case, shaped `6{year}{court}{document}{number}` from 1951, then `(nn)`, `R(nn)`, or an `_` suffix (off-pattern only `62011CN347`, `62014CN00016`, `62021CO0121_1`), with none of those openings anywhere else; other openings can sit mid-CELEX (`C0097` in `62023CC0097`, `J0131`, `0161R`, `RES`) or complete to no CELEX start (`12CJ0131`). A whole CELEX takes the same one-term route, not the keyword's exact family arm: the bounded family would drop `62021CO0121_1` for `62021CO0121` and its corrigendum link can add rows the scan never returned. Live, the generated queries returned identical rows to the scan: `2013CJ0131` 0.3 s against 14.3 s, `62014CJ0362` 0.3 s against 27.3 s, `CO0121` 0.5 s against 13.8 s, and a `date_from` search on `CJ0131` 0.7 s against 14.5 s.

**Document categories use explicit authority families; consolidations follow the basic-act edge**
The CELLAR resource-type authority publishes the variants as separate top concepts, without a hierarchy that can safely expand `REG`, `DIR`, or the other public categories. `eurlex_search_documents` therefore uses a reviewed exact-code family for each `document_type`; name-prefix matching is not part of the contract, and draft regulation/directive/decision/recommendation concepts remain proposal records rather than adopted-act family members. When `include_consolidated` is enabled, a `CONS_TEXT` work qualifies only when `cdm:act_consolidated_based_on_resource_legal` reaches a basic act in the selected family. The broader `cdm:act_consolidated_consolidates_resource_legal` relation is not used: it also points to amendments and prior consolidations, so `consolidated_version` traversal and `eurlex_get_document`'s consolidation lookup follow the based-on link too.

**Advocates General get their own field; authors are institutions only (#96)**
`cdm:work_created_by_agent` lists the Advocate General (a `cdm:person`) beside the court on case law, and the deciding court (a `cdm:court_national`) on sector-8 national decisions; both are CELLAR resources, not authority codes, so labelling them through the corporate-body table leaked UUIDs. `author_institution(s)` keep their "institution" contract: a national court is labelled by `cdm:court_national_name`, and person creators are dropped, since each is also that work's `cdm:case-law_delivered_by_advocate-general`. That predicate feeds `advocates_general`, surnames from `cdm:agent_name`, sorted, on `eurlex_get_document` and `eurlex://document/{celexNumber}`, both read through `work-agents.ts`. The query reads person and court names through separate `OPTIONAL` variables; one variable shared by two `OPTIONAL`s leaves the second unbound on CELLAR.

**Authors are labelled by their authority code's English `skos:prefLabel` (#103)**
Every authority-code author — a corporate body (`EURUN` "European Union", `EESC`, `OP_DATPRO` "Provisional data"), a member state from `country/` on national implementing measures and agreements, an MEP from `fd_013/` on parliamentary questions, and the `fd_014/` and `role-qualifier/` tables — is labelled by its English `skos:prefLabel`, read by an `OPTIONAL` on `?agent` in `fetchWorkAgents`' existing query under its own `?agentLabel` variable, so no query is added. Labels are de-duplicated (`EURUN` returns two identical label rows), and a code with no English label (only two `resource/agent` codes on 2026-09-25) keeps the last-path-segment fallback. The static `CORPORATE_BODY_LABELS` table it replaces covered 32 of the 598 corporate bodies that author works, 28% of corporate-body author links, and no other authority table; its short forms also failed to round-trip, since `eurlex_search_documents` matches `author_institution` against the same English prefLabels and `"Council of the EU"` matched no work. Keeping the table first and adding prefLabels for the rest was rejected: its ten drifted short forms would still not round-trip. A separate batched label query adds a round trip for no gain. Ten strings change as a result, e.g. "Council of the EU" → "Council of the European Union", "DG Competition" → "Directorate-General for Competition"; the output schema does not. Live (2026-09-25), `22026A00757`, `71991L0683NLD_87862`, `91980E001013`, and `51988AC0454` read "European Union" and 26 member states, "Netherlands", "European Parliament" and "VAN MIERT", and "European Economic and Social Committee"; both `32016R0679` labels return a non-empty `author_institution` page; `62012CJ0131` still reads "Court of Justice" with Advocate General Jääskinen.

**Relation pages order by a string date, then work URI (#100)**
Each relation direction is grouped per related work and paged newest-first. CELLAR evaluates `MAX` over the `OPTIONAL` `xsd:date` wrongly in that grouped query, attaching other works' dates and not the same ones on every call, so pages were neither the newest works nor stable. The aggregate is `MAX(STR(?relatedDate))`, since ISO dates sort lexically in date order, and both the per-direction subquery and the outer `UNION` order by `DESC(?relatedDateMax) ?relatedWork`: the work URI is the `GROUP BY` key, so the order is total and consecutive offsets neither overlap nor skip. An undated work's aggregate stays unbound and sorts last. `has_more` counts a sentinel row and does not depend on the order.

**Relation rows carry the related work's date and English title, joined after paging (#119)**
Each row returns `related_date` (the `?relatedDateMax` its page is ordered by) and `related_title`, the related work's English expression title, whole. The per-direction queries became subqueries of an outer query that adds one `OPTIONAL` English title per paged work, aggregated `MAX(STR(?relatedTitle))` (one value, the same on every call, for a work with several) and grouped by the subqueries' projected variables, then re-ordered `?direction DESC(?relatedDateMax) ?relatedWork`. Joining the title inside each arm returned the same rows but aggregated a title for every related work before `LIMIT` (2,291 for the GDPR's incoming citations), so its cost grows with the relation set; after paging, the join touches at most `limit + 1` works per direction. Live against v0.17.0 (2026-09-25), `32016R0679` `cites` and `32022L2555` `national_transposition` returned identical rows, order, `has_more`, and `next_offset`, every title matched an English `cdm:expression_title` of its work, and the query ran in under 0.5 s. A field the work lacks is omitted, with no other language standing in: national implementing measures are rarely titled in English (1 of the 304 `32022L2555` measures), so most `national_transposition` rows carry a date alone. Titles are returned verbatim rather than parsed as case law, since `#`-delimited titles are a small share of a relation page.

**Case-law titles decompose through one shared parser; the raw title returns only when the parse is incomplete (#116)**
`parseCaseLawTitle()` is the parser every tool that reads a CELLAR case-law title uses. It reads the leading segment for `formation` (the parenthetical after the court, verbatim, or the President / Vice-President / chamber President of an order so titled; never "(Extracts)", never inferred for a pre-chamber "Judgment of the Court of DATE.") and `advocate_general`, takes a "Request(s)/Reference(s) for a preliminary ruling from [the] X" or older "…: X - Country" segment as `referring_court` (the dash form "Reference for a preliminary ruling – …" is a keyword list and stays `subject_matter`), and anchors `case_reference` on "Case", "Cases", or "Joined Case(s)" (the "Joined" forms, 5.6% of 9,300 sampled titles, used to leave it unset and put the case list in `subject_matter`). A parse is complete when every non-empty segment lands in a field and the leading segment's date equals the record's date. A leading segment marking publication by extracts ("… of 15 September 2016 (Extracts).", `62014TJ0353`) still yields its formation and date, but no field says the text is an extract, so it counts as unplaced and the raw title stays. `eurlex_get_cases` omits `title` in both channels on a complete parse, since the raw string repeated the parsed fields and made up 34–43% of a row's structured bytes; an incomplete parse keeps it, so nothing the fields miss is dropped (#40). Dropping `title` from the text channel alone was rejected: structured-only clients would keep the duplication. On a 9,331-title sample, 97.9% of parses are complete (judgments 98.8%, orders 97.1%, AG opinions 96.3%); the remainder keep `title` — a leading segment of another shape, an extracts marker (53 titles), an unplaced segment, or a title date that differs from the work date (`62019CJ0793`). The text channel also drops the `Parties` line when it repeats the heading.

**Search pages order by date, then CELEX (#102)**
`eurlex_search_documents` and `eurlex_get_cases` order by `DESC(?docDate) ?celexNumber`. Ordering by date alone left records that share a date in an order CELLAR varied between calls, so identical calls returned different pages and consecutive offsets could repeat one record and never return another. The tiebreak is the `GROUP BY` key `?celexNumber`, not the projected `?celex`: Virtuoso does not sort on a `SAMPLE` alias of a string, and a `?celex` tiebreak returned same-date rows in a different order on each call.

**Date-bounded searches page first (#98, #105)**
When `eurlex_get_cases` or `eurlex_search_documents` has a `date_from` or `date_to`, a subquery selects the page's CELEX keys in the same total order (`SAMPLE(?date) AS ?pageDate`, `LIMIT`/`OFFSET`), and the outer query repeats the row pattern and aggregates only those keys; the flat form aggregated every match before paging. The row date is `?pageDate`, and the date stays `SAMPLE` at both levels: a `MAX` over the ordered date lets Virtuoso pick a date-index TOP-k plan that drops the upper-bound filter. The outer query tests the keyword as `FILTER EXISTS`, because re-joining it re-ran the full-text and CELEX arms over the corpus and made wide-range keyword searches slower than the flat form. In paired live runs against the tie-broken flat form, every shape returned identical rows and fields; a one-month range went from 9.5–46 s to 0.35–1.0 s, and a single `date_from` or `date_to` bound was faster too, so any bound selects the page-first form. A search with no date bound keeps the flat form: finding a broad browse's page keys costs about as much as the whole query. `eurlex_search_documents` also tests the author as `FILTER EXISTS` at the outer level, for the same full-text reason. Its date-bounded searches had passed the 55 s client timeout even for a single day; paged first, a month range, a single day, a single bound, and the keyword, EuroVoc, author, and consolidated-text combinations each returned identical rows in 0.6–1.6 s (a `REG` + half-month search went from 13.8 s to 1.4 s, a lone `date_from` from 110 s to 0.6 s). A keyword-only search stays flat, where it ran faster than paged first.

**Formex quotation marks render from their `CODE` (#99)**
Formex writes a quotation mark as `<QUOT.START CODE="2018"/>` / `<QUOT.END …>` (or an empty start/end pair), naming the character by its hex code point. `formexText()` turns a valid one into a character reference in place, which the single decoding pass renders with no padding, so XML outline titles match the HTML ones in every language; a missing, non-hex, out-of-range, surrogate, or control `CODE` is stripped as a tag, as before. Tag stripping matches `<[^<>]*>`, so a run of `<` with no `>` costs one pass.

**Headings are read in the served language (#107)**
The html/markdown outline and `select` match heading words on the rendered text (#12), so each of the 24 languages carries its own keywords for article, chapter, section, and annex, and the position of the number (`HEADING_FORMS` in `act-structure.ts`, measured on `32024R1689` in every language). Estonian, Finnish, Hungarian, Lithuanian, and Latvian put the number first in some or all (`1. cikk`, `I LUKU`); the number takes a trailing period (`Članak 1.`, Markdown's escaped `1\.`), the Portuguese ordinal (`Artigo 1.º`), French `premier` for article 1, and the Greek capitals Ι/Χ the Greek text writes for Roman I/X (`ΚΕΦΑΛΑΙΟ ΙV`). A Greek keyword also admits the accented vowels of its lower case, since Formex titles and annex subheadings write `Τμήμα 1` where the chapters write `ΤΜΗΜΑ 1`. The vocabulary is keyed by the language actually served, after any English fallback, rather than matching all 24 at once, which would read one language's heading word in another's text. Every heading is reported with its English label and a language-neutral number (`IV`, `1`) in every format, a Formex article included (`4. cikk` is `Article 4`), so the outline, `selection.matched`, and `selected_sections[].label` read the same whichever format a caller switches to; only a Formex article with no number to read keeps its own heading text. A selector token may carry an English kind word or one of the served language's, before or after the number (`Artikel 1`, `1. cikk`, French `Article premier`), and is split into words rather than matched with a whitespace-spanning pattern, so a caller-sized token reads in one pass. Structural markup was rejected for html: ELI ids are missing on Greek and Romanian annexes, carry a trailing space in three languages, and use Greek letters in Greek chapter ids, and Markdown drops them anyway. A Formex article is numbered from its `<ARTICLE IDENTIFIER>` (`001` → `1`, `006A` → `6A`), language-neutral where the heading text is not, and from the heading text when the identifier is absent or of another shape; its chapter and section titles take the same vocabulary.

**Quoted amending text is not the act's own structure (#106)**
An amending act quotes the articles, sections, and annexes it inserts into another act, and those headings read like its own. Counting them listed another act's articles in the outline, ended the amending article at its first quoted heading, and let `select` resolve a number that exists only in the quoted text. Each format marks quoted text differently. Formex wraps it in `<QUOT.S>`, so a `<TI.ART>` or chapter/section `<TI><P>` opener inside one, at any nesting depth, is skipped. CONVEX HTML puts each amending point in a numbering table and the quoted headings in its cells, so a chapter/section/article/annex heading line whose text sits inside a `<table>` is skipped; an act's own headings never do (none in `32016R0679` EN/FR/DE or `32024R1689` in any of the 24 languages). Recitals are table cells by layout and are exempt. Markdown flattens the tables, so the content service parses a Markdown body's headings against the wire HTML it was rendered from and returns them with the body (`FetchContentResult.headings`), and the two heading sequences are aligned in order: each Markdown heading takes the verdict of the next HTML heading of the same kind and number, and an HTML heading may be passed over only when it sits in a table. The sequences are not identical in general, and every difference seen is an in-table HTML heading the Markdown lacks: a quoted heading whose opening `‘` sits on a line of its own renders as `‘ Section 3` (`32019R0876`: 176 HTML headings against 175), and a genuine table's cells render as a GFM row (`12016M/TXT`: 91 in-table headings). When a Markdown heading has no counterpart, or an HTML heading outside any table would be passed over, every Markdown heading is kept, the behavior before this rule, since a misplaced verdict could drop one of the act's own headings. The HTML sequence is read with the html path's own line splitter (#126), so a legacy `text/html` body written on one line aligns like a CONVEX one (`31995L0046`: 43 headings in each). Equal positions were rejected: one lost heading shifted every later verdict, so CRR2's Markdown fell back to all 175 headings, quoted ones included. Quote-mark tracking was rejected (English writes `’` as the apostrophe, and only the first heading of a quoted run carries `‘`), as was a monotonic article-number filter (an insertion can continue the act's own numbering). Both depth scans read each tag once and move forward only, so unclosed openers stay linear (#94). The alignment reads both sequences once, forward only. The HTML behind a Markdown body is about 2× the Markdown's length on most acts and from 1.06× (`31995L0046`) to 5.7× (`32019R0876`: 4,806,352 characters behind 846,804) across 40 cached act/language pairs, so it is read once, at conversion, and dropped there: only the heading list outlives the conversion, in the body cache (#127). Parsing it roughly triples the Markdown heading parse (`32016R0679` EN: 7.5 ms against 2.6 ms; `32019R0876`: 25.8 ms against 6.0 ms), a cost paid once per cached body and on every Markdown fetch, outline or not.

**Recitals collapse in the outline (#118)**
The preamble's recitals were most of an outline (173 of the GDPR's 298 entries), ahead of the chapters and articles a caller reads it for. The default outline collapses each run of consecutive recitals into one entry, `{ kind: "recital", number: "1–173", label: "Recitals 1–173", offset: <recital 1> }`, labelled in English like every other entry, and a lone recital keeps its own; `include_recitals: true` lists them individually. `kind` stays in the five-value vocabulary, so a caller filtering by kind still finds the preamble; `number` becoming a range is the contract change. `select` resolves against the uncollapsed headings, so any single recital stays reachable, and it ignores `offset`/`limit`: a selection is capped at 100,000 characters with no continuation (#80), each section addressed by `selected_sections`. Opt-in collapse was rejected: every caller that never set the flag would keep the noise.

**Legacy html bodies end a line at each block tag (#126)**
Acts CELLAR serves only as legacy `text/html` (`31968R1612`, `31995L0046`, `32000L0031`, and their peers, 1968–2002) write the whole act as one line of `<p>…</p>` paragraphs, so the line-by-line heading match found nothing in html while their Markdown outlined fully. On the html path a block tag (`p`, `div`, `br`, `h1`–`h6`, `li`, and the table, row, cell, and table-section tags) also ends a line, each segment keeping its offset in the body as served, and a tag preceded only by whitespace on its line does not split it, so CONVEX, which writes one indented tag per line, keeps every offset: splitting before every block tag moved 272 of the GDPR's 298. The body itself is never rewritten: html passes through verbatim, and outline offsets index the string the caller pages (#12, #48). `&quot;`, which four of the six sampled legacy bodies use, joined the named references heading text decodes. The split is one linear pass per line.

**Chapter and section headings may carry their title in capitals (#130)**
Legacy bodies write a chapter's title on its heading line (`<p>CHAPTER I GENERAL PROVISIONS </p>`, `ΚΕΦΑΛΑΙΟ I ΓΕΝΙΚΕΣ ΔΙΑΤΑΞΕΙΣ`, `I LUKU YLEISET SÄÄNNÖKSET`), and the Finnish one a section's too (`I JAKSO TIETOJEN LAATUA KOSKEVAT PERIAATTEET`), so `31995L0046`'s seven chapters went unlisted and unselectable in html and Markdown alike. A chapter or section line may now continue past its heading with a title that has a capital letter and no lower-case one (`\p{Lu}`/`\p{Ll}`, so Greek and Cyrillic are read like Latin; German `ß` is allowed), and that text becomes the heading's title. A prose cross-reference ("Chapter V on the transfer of…") always runs into lower case, so it stays unmatched. The case test runs apart from the heading pattern, whose case-insensitive flag makes `\p{Lu}` and `\p{Ll}` match either case. Accepting any inline title was rejected, since it would read those cross-references as headings. Outlines of `32016R0679`, `32024R1689` (Greek), and `02016R0679-20160504`, in html and Markdown, are unchanged.

**Legacy recitals may open without a parenthesis, and a number-first article keyword may be inflected (#131)**
The Finnish and Swedish legacy bodies of `31995L0046` number their recitals `1)` … `72)`, and the Finnish one heads its last article `34 artiklan`, the keyword in the genitive, so its outline had no recitals and 33 of 34 articles. A preamble recital marker is now `(N)` or `N)`, still read only before the first enacting heading, so an article's `1)` sub-point stays out. In a language that writes the article number before the keyword (Finnish, Hungarian, Lithuanian, Latvian), an article line standing alone may carry lower-case letters after the keyword, the case ending those languages attach, and nothing else, so `34 artiklan 1 kohta` stays prose; the keyword-first forms are unchanged, so `Articles 12` is not an article. Outlines of `31995L0046` EN and DA, `32000L0031` FI (which writes `(N)`), and `32016R0679` EN and FI, in html and Markdown, are unchanged, offsets included. The Swedish body's sections, headed `AVDELNING`, stay unlisted: Swedish acts use that word for a title, the level above a chapter, and titles are not a detected kind.

**Case law carries its ECLI, a parsed title, and a heading and operative-part outline (#117)**
A judgment was read as if laid out like an act: its title was CELLAR's raw `#`-joined string, it had no `ecli`, and `outline` was empty, so reaching the ruling of `62012CJ0131` meant paging a 77,394-character Markdown body whose operative part starts 95% of the way in. A sector-6 work now differs in three places.

- **`ecli`** follows `eurlex_lookup_celex`: the resolved work's own, else the lowest any work of the CELEX records. Both ride the core metadata query as `MIN(STR())` aggregates, added only for a sector-6 CELEX, so no query is added and legislation's query is unchanged. Across every CELEX starting `62014C` or `62023T` that carries an ECLI (1,928, 2026-09-25), the canonical work always carried it.
- **`title`** goes through the #116 parser, fed the English title in every language (#133). On a complete parse it is the parties, or the court/AG descriptor of a case with none, and `formation`, `referring_court`, `subject_matter`, and `case_reference` carry the rest; the court, date, type, and Advocate General were already fields. An incomplete parse keeps the raw title. The fields are filled either way, as `eurlex_get_cases` fills them.
- **The outline** lists each top-level section heading as kind `heading`, labeled as served and numbered by its 1-based position, and a judgment's or order's ruling as one `operative_part` entry labeled "Operative part", both rank 1: a headed section ends at the next heading or at the operative part, which runs to the end of the body. `select` takes `headings` (positions) and `operative_part` (a flag). An AG opinion has headings only.

The parser is chosen by the CELEX, not by the body (`parseDocumentStructure`): sector 6 is case law, and a CELEX whose document letter is `J` or `O` is a judgment or order with a ruling. A body-driven choice would read an act that quotes "On those grounds" as a judgment. Because the choice is a function of the CELEX, the Markdown heading list the body cache keeps under that CELEX (#129) is always the case-law parser's.

Headings come from level-2 heading markup, which is language-neutral, in each generation CELLAR serves: `p.title-grseq-2` in CONVEX xhtml, `p.coj-sum-title-1` in `coj-` xhtml, `P.C04Titre1` in the text/html Word export of recent General Court judgments, `<h2>` in legacy text/html, and `<GR.SEQ LEVEL="2">` titles in Formex. The `coj-` generation also writes its document header in `coj-sum-title-1`: the court and date lines and an opinion's "OPINION OF ADVOCATE GENERAL" / "SZPUNAR" lines are plain text, while a section heading opens with a `coj-bold` span, so only bold ones count. The bold "Judgment" / "Arrêt" title is excluded as the first bold heading before paragraph 1 of a judgment or order. Position alone cannot separate header from section: "Background to the dispute" (`62014TJ0353`) and an opinion's "Introduction" (`62023CC0135`) both precede paragraph 1. The Formex "Judgment" title is `LEVEL="1"`, and the Word export's is `C75Debutdesmotifs`, so neither needs a rule. A legacy text/html AG opinion opens its text with `<a name="OP"/>` and an `<h2>` naming the document ("Opinion of the Advocate-General", `62006CC0341`) that would span the whole opinion, so the `<h2>` right after that anchor is left out; the anchor, like the `DI` one below, reads the same in every language. A fixed phrase set ("Legal context", "Costs", …) was rejected. It varies by procedure (preliminary reference, appeal, direct action) and era ("Le cadre juridique" in 2014, "Cadre juridique" in 2026), and a section would run across any heading it missed: on `62012CJ0131` the dispute section would have spanned 58.8k Markdown characters instead of 9.1k.

In html the operative part is the legacy `<a name="DI"/>` anchor where there is one, else the last paragraph opening with the served language's formula (`OPERATIVE_FORMULAS`, one per language as `HEADING_FORMS` is); in Formex it is `<JURISDICTION>`. A table of contents links to `#DI` near the top of a legacy body, so matching the words "Operative part" would land there. CONVEX lays the formula out in a layout-table cell, the very markup #106 reads as quoted text, so the case-law parser applies no table filter, and the operative part starts at the outermost table holding the formula, so html slices stay whole tables. A heading after the operative part's start belongs to it, as the legacy `<h2>Operative part</h2>` after its anchor does.

The formula is verified live in EN, FR, and DE (`62012CJ0131`), in ES, IT, NL, PL, SV, LT, HR, and EL (`62019CJ0311`), and in PT, DA, FI, HU, ET, and BG (`62018CJ0311`). Dutch has no lead-in phrase: its ruling opens "Het Hof (Vierde kamer) verklaart voor recht:", so the Dutch entry matches the court, a verb of ruling, and a closing colon, each gap bounded at 100 characters so a long paragraph with no period costs linear time rather than quadratic. Croatian writes both "Slijedom navedenog" and "Slijedom navedenoga" (`62018CJ0311`), and the entry takes either. The other seven languages (CS, LV, MT, RO, SK, SL, GA) carry the Court's standard wording, best-effort, and a language whose formula does not match still gets its headings.

Markdown drops the markup, so the content service reads the landmarks from the source HTML and finds each in the Markdown in order: the next line after the previous landmark whose text matches, stripped of ATX markers, escapes, and emphasis, and an ATX line for an `<h2>`. An in-order match passes over a legacy table of contents, which renders the same words as plain lines. Numbers are the HTML's, so `select.headings` names the same section in every format. Without source HTML, the operative part alone is found by its formula. Across four html generations, Formex, and three languages, html, Markdown, and xml give the same labels.

Legislation is untouched. Against v0.17.0's parser, the outlines (collapsed and not) and five selector sets matched byte for byte on 64 body/format pairs (7,976 headings): live act bodies in html and Markdown, among them `32016R0679`, `31995L0046` in five languages, `02013R0575-20260626` EN and DE, and `32015R2120` xml, plus every act test fixture.

**The document title follows the served language; case law parses its English title (#133)**
`eurlex_get_document` read only the English expression title, so `language: "fr"` served French text under an English title. The core metadata query now also reads the requested language's expression title, through its own `?languageExpr` variable and a `MAX(STR())` aggregate (as #119's related titles, so a work with several titles in that language returns the same one on every call), when that language is not English; the metadata stays one query, and English asks for nothing extra. The body settles the served language — the requested one, or English after a fallback — and `title` follows it: the requested language's title, or English when CELLAR records none in that language (older acts carry no Irish expression) or the body fell back. Without a body (`metadata_only`) the served language is the requested one. Case law is the exception: the #116 parser reads English segment shapes only ("Judgment of the Court", "Request for a preliminary ruling from", English month names, "Case"), and CELLAR's French title of `62012CJ0131` opens `Arrêt de la Cour (grande chambre) du 13 mai 2014.#… contre …#Demande de décision préjudicielle, introduite par l'Audiencia Nacional.`, which none of them match, so a sector-6 record parses its English title in every language and its `title` and parsed fields stay English; only a record with no English title shows the served language's raw title, unparsed. Localizing the parser to 24 languages was out of scope. The `eurlex://document/{celexNumber}` resource takes no language and keeps the English title. Live (2026-09-25), `32016R0679` returned its French and German titles, `31995L0046` in Irish its English one, and `62012CJ0131` in French the English-parsed parties with its Grand Chamber formation and referring court.

**Consolidated point labels join their text (#120)**
Consolidated versions (`0YYYYTNNNN-YYYYMMDD`) lay points out as CSS-grid divs rather than OJ numbering tables, so each label rendered as a Markdown paragraph of its own (761 label-only lines in `02016R0679-20160504`). Before conversion a `div.grid-container.grid-list` row becomes its `.grid-list-column-2` text with the `.grid-list-column-1` label in front, and a `span.no-parag` number moves into the element after it, at the start of its first `<p>`/`<div>` block or its bare text, innermost row first. The label moves as markup with its `<span>` wrappers dropped, so a number stays one run with its text (escaped `1\.` where line-initial) and an amendment marker linked beside a label keeps its link. Every legacy `text/html` page also opened with a `<div id="banner">` legal-notice strip, now stripped as chrome. OJ acts are unchanged byte for byte.

**Markdown converts block by block (#127)**
The whole-body conversion serialized the pre-processed body back to a string (3.3 million characters for `32019R0876`) that node-html-markdown then parsed into a second whole-act DOM with its own bundled parser; the consolidated CRR (`02013R0575-20240709`, 10.2 million characters of HTML) peaked at 1,559–1,612 MB for one Markdown outline. After chrome stripping, table flattening, and label joining, the body is walked instead: a `<div>` holding elements is descended into, every other block element is translated alone by one `NodeHtmlMarkdown` instance, each run of inline children between blocks is translated together as the paragraph it forms, and the pieces are joined by blank lines. A flattened numbering table is spliced in as its `<div>` rather than as a parsed fragment root, so the walk can descend into it: as a tagless root it was an inline run, and `32019R0876`'s outermost amending table sent 3.2 million characters to one call. The largest single translation is now a genuine data table (the CRR's 674,870-character correlation table in Annex IV). Peak RSS for a Markdown outline, bare Bun 1.4.2 on macOS arm64, three runs each: `02013R0575-20240709` 1,559–1,612 MB → 637–638, `32019R0876` 560–617 → 291–295, `32024R1689` 117–120 → 111–120, `32016R0679` 97–102 → 94–98. Block translation alone changes nothing but line-end whitespace and blank-line runs: against the whole-body conversion of the same pre-processed body, on 46 cached act/language bodies, the Markdown differs only there, with every outline label and title unchanged (offsets move with the whitespace, measured on the string served). The label joining and banner stripping of #120 are separate changes to the Markdown, outside that comparison. Importing node-html-markdown's visitor to hand it the existing DOM was rejected (internal, and built on a different node-html-parser major), as was replacing the converter (the GFM table behavior of #13 to re-prove).

**Served bodies are cached in process (#127, #129)**
Every page of a paged read fetched the whole body again, and in Markdown converted it again: 85 fetches of 10.2 MB and 85 conversions to read the consolidated CRR at the default `limit`. `EurLexContentService` keeps an LRU of available bodies keyed by CELEX, requested language, and format, holding the served text, the served language and fallback note, and for Markdown the heading list parsed once against the source HTML (#106), never the HTML itself. The same string is served on every page, so offsets measured on one page hold on the next (#12, #48, #80). An entry lasts one hour (CELLAR text per CELEX does not change; corrigenda and consolidations get their own CELEX), and retained characters — text, note, and heading strings — are capped at 16 million, least recently used first out; an entry over the cap alone is not stored. Measured retention matches two bytes per character (every sampled Markdown body holds non-Latin-1 text): 4.2 MB for the CRR's 2,105,086-character Markdown and 783 headings, 7.2 MB for the four acts above against 32.5 MB of source HTML, so the cap bounds the cache near 32 MB. A hit takes under 0.05 ms against 54–541 ms for a cold Markdown call from a local body (1.2 s live for `32016R0679`). Only available bodies from calls whose signal has not aborted are stored, so an unavailable body (#18, #68) or a cancelled call leaves nothing. The cache is process-wide rather than `ctx.state`: act text is public and the same for every tenant, and `ctx.state` is tenant-scoped and JSON-serialized. Cold calls are not merged: each fetch is bound to its own caller's signal, so one caller's cancellation never reaches another, at the cost of a duplicate fetch when two callers miss at once.

**Caller URIs are checked against the whole IRIREF exclusion set (#140)**
`work_uri` (on `eurlex_get_document` and `eurlex_get_relations`) and `eurovoc_concept` reach their query as `<${uri}>`, so each schema rejects U+0000–U+0020 and `` <>"{}|^`\ `` (SPARQL 1.1 grammar rule [139]) plus any other Unicode whitespace. The check covered only whitespace, `<`, `>`, and `"` before this, and CELLAR answered each of the rest with SP030, leaking the internal query (U+0000 came back as an HTTP 500). Real work and EuroVoc URIs hold none of these characters.

**`eurovoc_concept` accepts only EuroVoc concept URIs, normalized to the http form**
The filter requires the EuroVoc namespace. `cdm:work_is_about_concept_eurovoc` binds only `http://eurovoc.europa.eu/` concepts (#11) — all 7,269 EuroVoc objects in CELLAR sit under that form — and `eurlex_browse_subjects` returns only it. `https://eurovoc.europa.eu/…` and an upper-case scheme or host name the same concept, so the filter rewrites them to the http form before the IRI check and the query, rather than rejecting a value it can map one-to-one. Any other URI (an ELI, a CELLAR work, another authority table, a lookalike host such as `eurovoc.europa.eu.example`) could match no work, and neither could the bare namespace, so each fails validation with a message naming the namespace, where before it returned an empty page.

**A lexical-safety test gates caller input in generated SPARQL (#64)**
`tests/sparql-lexical-safety.test.ts` walks the Zod shape of every tool and resource, sends each top-level string input hostile values — quotes, backslash, angle brackets, `` {}|^`* ``, CR, LF, tab, U+0001 together, plain, behind a leading `"`, and behind the ECLI, ELI, EuroVoc, and CELLAR-work prefixes, plus one value per IRIREF-excluded character behind each prefix so a guard missing a single character is caught — and lexes every query the handler hands the mocked CELLAR service. Required sibling inputs are seeded from the schema (first enum value, literal, or a benign string), and each case must first show a benign value parses with them, so a schema that rejects every variant cannot pass the case vacuously. A caller value must land inside a well-formed short string literal, IRIREF, or `bif:contains` expression, in the triple or the `FILTER(bif:contains(…))` form: phrases of letters, digits, and spaces, or prefix terms of at least four letters or digits ending in `*`, joined by `OR`. Every `<` not followed by `=` or whitespace is lexed as an IRI. An input rejected before any query is built passes, so constrained, derived, and constant interpolation sites need no allowlist. Exempt are `eurlex_query_sparql.sparql_query`, which takes caller SPARQL by design, and the nested `eurlex_get_document.select.*` strings, which only select sections of fetched text; any other nested string input fails the coverage test until it is tested or exempted. The free-text and URI inputs must each reach a query, so a harness that stops reaching a builder fails rather than passing vacuously. A static lint on `"${…}"` and `<${…}>` was rejected because it needs dozens of allowlist entries and cannot see an escape dropped where `buildEliQuery` or `buildEcliQuery` is called. Branded literal and IRI types were rejected because they would rewrite every interpolation for the same guarantee. A runtime lexer in the service was rejected because it catches a malformed query only in production.

**Resources are supplementary**
`eurlex://document/{celexNumber}` covers the `tools/list`-stable URI use case; the content is fully reachable through `eurlex_get_document`. No unique data lives only in resources.

## Error Contracts

Typed error contracts for each tool — these become the literal `errors: [{ reason, code, when }]` entries during implementation. Baseline infrastructure errors (`InternalError`, `ServiceUnavailable`, `Timeout`, `ValidationError`) bubble freely from the service layer and don't need declaring per tool.

**`eurlex_search_documents` / `eurlex_get_cases`**
| reason | code | when |
|:-------|:-----|:-----|
| `no_filters` | `ValidationError` | `eurlex_search_documents` only: no narrowing filter was supplied, so the query would scan the whole corpus |
| `invalid_date_range` | `ValidationError` | `date_from`/`date_to` is not a real calendar date, or the range is inverted |
| `invalid_case_number` | `ValidationError` | `eurlex_get_cases` only: `case_number` is not a recognizable case number and holds characters no CELEX contains, names more than one case, or is a prefix-less number dated outside 1953–1988 |
| `invalid_author_institution` | `ValidationError` | `eurlex_search_documents` only: `author_institution` holds no letters or digits, so it can name no institution |
| `invalid_keyword` | `ValidationError` | `keyword` holds no letters or digits, so no title and no CELEX can match it |
| `sparql_error` | `ServiceUnavailable` | Virtuoso returned HTTP 200 with `Virtuoso 37000 Error` body; query is malformed or timed out |

> **Zero hits is an empty page, not an error (#112).** An empty first page from `eurlex_search_documents`, `eurlex_get_cases`, `eurlex_browse_subjects`, or `eurlex_get_relations` returns the same shape as an exhausted later page — `total: 0`, `has_more: false`, no `next_offset`, plus `query_echo` or `requested_relation_types`/`empty_relation_types` — with an enrichment `notice` naming what matched nothing and how to broaden it. A thrown `NotFound` read as a broken call and invited retrying the same query. A page past the end carries no notice. Only input the server can prove wrong stays an error: an `author_institution` with no letters or digits is `invalid_author_institution` and a `keyword` with none is `invalid_keyword`, while a well-formed author or keyword matching nothing is an empty page. A page with more rows carries a `notice` naming the next offset, alongside `truncated`/`shown`/`cap`. A notice quotes each filter value to at most 100 characters plus an ellipsis, as do the validation messages that quote one; `query_echo` keeps the whole value.

> **Case numbers match every document letter the court files (#81, #91).** A case-law CELEX reads `6{year}{court}{document}{number}`, and one case spans several document letters (judgment `CJ`, order `CO`, AG opinion `CC`, …). `case_number` fixes year, court letter, and number and matches the court's document letters — `C`: `J O C P S T D`, `T`: `J O C T`, `F`: `J O`, plus the notice letters `A B N` when `include_derivative` admits derivatives — as an unanchored `REGEX` (echoed as `celex_fragment`, e.g. `2023C*0097`), which confirms the CELEX full-text index hits of one prefix term per admitted letter (#138). The Court of Justice's numbered Opinions and Rulings (`CV`, `CU`, `CG`, `CX`) are left out: they are cited as "Opinion 2/13" and their CELEX collides with the `C-n/yy` case of the same number. Text after the year is ignored as a procedural suffix unless it holds another case designation (a digit, `/` or a hyphen, a digit): "C-131/12 and C-132/12" is rejected as `invalid_case_number` rather than answered for C-131/12 alone. `court` keys on the court letter alone (`FILTER(SUBSTR(STR(?celexNumber), 6, 1) = "C")`), so every record a court filed stays reachable whatever its document letter, derivatives still only under `include_derivative`. A value that parses as no case number keeps the case-insensitive CELEX-substring match only when made of CELEX characters `[0-9A-Za-z()_]` — every sector-6 CELEX is, so nothing else can ever match there and is rejected as `invalid_case_number` instead of answered with an empty page. That match runs on the CELEX full-text index when the value opens with the sector and year, the year and both letters, or both letters and the number, and scans every CELEX otherwise (#134).

A well-formed identifier that matches no work returns `found: false`, not an error, with an enrichment `notice` naming the CELEX, ELI, or ECLI tried (and the citation it was parsed from), the CELEX pattern, and `eurlex_search_documents` with `keyword`.

> **OJ citations resolve through the CELEX branch (#114).** Under `identifier_type: "auto"`, a citation that names its act type and year maps to `3{year}{letter}{number}`, the number zero-padded to four digits: `Regulation (EU) 2016/679` → `32016R0679`, `Regulation (EC) No 1049/2001` → `32001R1049`, `Directive 95/46/EC` → `31995L0046`, `Decision No 3632/93/ECSC` → `31993S3632`. `No` before the numbers means number/year, the form used before 2015; otherwise the order is year/number. The marker, not number plausibility, decides: `No 596/2014` and `2015/596` are different acts, and `46/95` has two plausible two-digit years. A two-digit year is 19YY. The act type sets the letter — Regulation `R`, Directive `L`, Decision `D`, Framework Decision `F`, Joint Action and Common Position `E` — and the ECSC domain turns a Decision into `S`; live CELLAR carries each of these (2026-09-25) and not the naive `D` for the ECSC, JHA, and CFSP forms. An institution or an Implementing/Delegated qualifier before the act type changes nothing (`Commission Implementing Regulation (EU) No 540/2011` → `32011R0540`), so only words may precede it; after the numbers only a `/domain` suffix and the ` of …` that opens a full title may follow, so two citations joined by "and" raise `ambiguous_identifier`. A citation without its act type is not parsed, because it is not one-to-one: `95/46` is Directive `31995L0046`, Commission Decision `31995D0046`, and Regulation (EC) No 46/95. Nor is one without a year (`Regulation No 17`). Returning every candidate for a type-less citation was rejected: it needs a list output the single-work contract lacks. A miss is a `notice` on the enrichment surface rather than new output fields, and `identifier_type` gains no `citation` value: CELEX, ELI, and ECLI output is unchanged, and the `ambiguous_identifier` reason and code stay as they were.

> **OJ references dropped as an identifier type (#5).** Live CELLAR research found no resolvable path: an OJ reference like "OJ L 119" has no literal in CELLAR (the journal issue appears only as cellar-UUID and `oj:JOL_…` token forms), the issue-level resource maps to multiple acts (OJ L 119/2016 → GDPR + the Police and PNR Directives), and the reference carries no year. Resolution is CELEX (`cdm:resource_legal_id_celex`), ELI (`cdm:resource_legal_eli`, an `xsd:anyURI` literal), and ECLI (`cdm:case-law_ecli`) only; an act citation that names its act type and year is parsed to its CELEX first (#114), which an OJ issue reference cannot be.

> **ECLIs resolve by a typed exact match (#84).** `cdm:case-law_ecli` is an `xsd:string`-typed literal: an untyped literal matches nothing, and `FILTER(STR(?ecli) = …)` scans, so the lookup joins `VALUES ?ecli { "…"^^xsd:string }`. Every EU ECLI is uppercase (`^ECLI:EU:[CTF]:\d{4}:\d+$`), so the uppercased form is sent alongside the caller's spelling; national ECLIs keep mixed case (`ECLI:FI:HelHO:2015:1766`), so an exact-spelling row wins. One ECLI can reach several works — two work URIs sharing a CELEX, `_RES`/`_SUM` siblings, an `_EXT` extract, a joined AG opinion's second CELEX — so derivative-typed CELEX numbers are set aside and the lowest CELEX left wins; the work within that CELEX follows the canonical-work rule below (#97). No work carrying an ELI carries an ECLI, so the shared ELI query binds none. `eurlex_get_cases` binds each row's ECLI with an `OPTIONAL` in its grouped query (`MAX(?caseEcli)` per CELEX group), at the outer level when a date bound puts the page keys in a subquery (#98). An ECLI names the case, not one work: a CELEX lookup reports the resolved work's ECLI, else the lowest ECLI any other work of that CELEX records, since a canonical work can carry none while its `do_not_index` copies do (`62015TO0235(01)`).

> **CELEX lookups bind a typed literal (#92).** Every CELEX literal in CELLAR is `xsd:string`-typed (sampled across sectors 0–7, C, and E), so each query keyed on a caller's CELEX — `eurlex_lookup_celex`, the shared CELEX → work resolution, and `eurlex_get_document`'s consolidation query — writes the CELEX through `celexLiteral()`, either as the object of `?work cdm:resource_legal_id_celex "…"^^xsd:string` or in `VALUES ?celexNumber { "…"^^xsd:string }`. Both resolve from the index in well under a second and return the same works as `FILTER(STR(?c) = "…")`, which scans every CELEX literal and took seconds. An untyped literal matches nothing, so the datatype is load-bearing. Metadata and relation queries then key on the resolved work's IRI, not the CELEX.

> **A CELEX held by several works resolves to one canonical work (#97).** CELLAR holds 14,265 CELEX numbers under more than one work (2026-09-25): `cdm:do_not_index` copies on case law and preparatory acts, and on three General Court CELEX a work aliased `…_EXT`. Exactly one of them is `owl:sameAs <http://publications.europa.eu/resource/celex/{CELEX}>`, the IRI the content resolver serves the body from; `work-resolution.ts` picks that work, else the lowest work URI, independent of row order. The alias IRI is built in SPARQL with `ENCODE_FOR_URI` (CELLAR stores `(`/`)` as `%28`/`%29`, which `encodeURIComponent` leaves literal) inside a filtered `OPTIONAL` in an ungrouped query; a `VALUES` + `BIND(EXISTS …)` form returned the same rows in ~20 s, and the `OPTIONAL` inside a grouped query never binds. `eurlex_lookup_celex` carries the pattern in its own query; `eurlex_get_document`, both `eurlex://document` resources, and `eurlex_get_relations` resolve through `resolveCelexWorks` and then key every query on the resolved work, so a CELEX-keyed join can no longer read the union of all its works. `eurlex_get_cases` and `eurlex_search_documents` resolve a page's CELEX values in one follow-up `VALUES` query; their grouped `MAX(?titledWork)`/`SAMPLE(?work)` stay as the fallback. The other works are not reported.

> **Bare work-level ELIs resolve via `/oj` normalization (#5).** CELLAR stores only the OJ-manifestation literal (`…/{number}/oj`), so the common bare citation form (`http://data.europa.eu/eli/reg/2016/679`) misses on exact match. A bare work-level ELI (`{type}/{year}/{number}`, no manifestation suffix) that returns no rows retries once with `/oj` appended — deterministic and one-to-one (verified live across regulation `32016R0679`, directive `32016L0680`, decision `32013D1313`, each `COUNT(DISTINCT ?work) = 1`). Manifestation-suffixed ELIs (e.g. a `/YYYY-MM-DD` consolidated version) are excluded from the retry, so a missing consolidated version never silently falls back to the original act.

| reason | code | when |
|:-------|:-----|:-----|
| `not_found` | `NotFound` | CELEX not found — resolve with `eurlex_lookup_celex` first. A `work_uri` is used as given and not checked, so an unknown one returns an empty page whose notice points to `eurlex_get_document` |

A work with no edges of the requested types returns an empty page with a `notice`, not an error.

**`eurlex_browse_subjects`**

No typed errors: a keyword that matches no concept returns an empty page with a `notice` suggesting a broader term, and a retry in English when the search was in another language.

**`eurlex_query_sparql`**
| reason | code | when |
|:-------|:-----|:-----|
| `not_read_only` | `ValidationError` | The query is a SPARQL 1.1 Update (`INSERT`, `DELETE`, `WITH`, `LOAD`, `CLEAR`, `CREATE`, `DROP`, `COPY`, `MOVE`, `ADD`) — rejected before any request |
| `unsupported_query_form` | `ValidationError` | Any other non-SELECT: `ASK`, `CONSTRUCT`, `DESCRIBE`, an unrecognized keyword, or no query after the prologue — rewrite as SELECT |
| `sparql_error` | `ValidationError` | Virtuoso returned a syntax/semantic error — fix the SPARQL query |
| `sparql_timeout` | `ServiceUnavailable` | Query exceeded the 60s Virtuoso hard limit — add more specific filters or reduce scope |

A zero-row result whose query has an untyped string literal as a triple object returns an empty page with a `notice` to type or language-tag it, not an error.

**Virtuoso error classification note:** Virtuoso returns HTTP 200 even for errors; the response body starts with `Virtuoso 37000 Error SP030:`. The service layer must inspect the body and throw `ServiceUnavailable` (transient/timeout) or `InvalidParams` (syntax error) rather than treating any HTTP 200 as a success.

## Known Limitations

- **No full-text body search**: SPARQL keyword search applies to titles and CELEX strings only. Deep full-text search across act body text requires the EUR-Lex registered-user web service (SOAP, requires EU login) — out of scope.
- **Title sparsity**: `cdm:work_title` is populated for most legislative acts but absent for many CJEU judgments and older works. Tool outputs must treat title as optional.
- **Case-law outline coverage**: a case-law body outlines only from heading markup it carries. Older AG opinions (`62012CC0131`, written in `sum-title-1`/`subtitle` classes), short legacy ones (`61985CC0156`), legacy opinions whose only `<h2>` is the title (`62006CC0341`), and summary-only bodies (`62010TJ0279`, `62010CO0091`) carry none, so they outline empty; the outline has no paragraph-level entries. The operative formula is verified live in 17 of the 24 languages (see #117 above).
- **Language availability**: older acts (pre-2004 accession) may lack EN translations. Some newer acts exist only in the language of the originating institution.
- **Relation graph depth**: `eurlex_get_relations` returns direct one-hop relations only. Multi-hop traversal (e.g., full amendment chain back to 1990) requires multiple calls or a `eurlex_query_sparql` query.
- **Consolidation**: the "current consolidated text" is a separate CELEX-numbered work, not a flag on the original. `eurlex_get_relations` surfaces it via the incoming `cdm:act_consolidated_based_on_resource_legal` edge (the forward `…has_consolidated_version…` predicate carries zero triples); fetching the consolidated text requires a follow-up `eurlex_get_document` call, or `resolve: "current_consolidated"` in one.
- **60-second Virtuoso timeout**: all generated SPARQL includes `LIMIT` enforcement at the service layer. Complex queries (deep relation traversal, large UNION blocks) can still time out. The `SPARQL_QUERY_TIMEOUT_MS` config gives a client-side abort before Virtuoso's hard cut.

## API Reference

### SPARQL Endpoint

- **URL**: `http://publications.europa.eu/webapi/rdf/sparql`
- **Method**: POST
- **Content-Type**: `application/x-www-form-urlencoded`
- **Body**: `query=<url-encoded SPARQL>` (or `query=...&format=application%2Fsparql-results%2Bjson`)
- **Accept**: `application/sparql-results+json`
- **Timeout**: 60 seconds (Virtuoso hard limit); enforce client-side at 55s
- **Error shape**: plain text `Virtuoso 37000 Error SP030: ...` (HTTP 200 status even on SPARQL errors — service must inspect the body and classify: syntax/semantic errors → `InvalidParams`; timeout messages (`SP031`) → `ServiceUnavailable`)

**Required PREFIX declarations:**
```sparql
PREFIX cdm: <http://publications.europa.eu/ontology/cdm#>
PREFIX skos: <http://www.w3.org/2004/02/skos/core#>
PREFIX xsd: <http://www.w3.org/2001/XMLSchema#>
```

**Result binding shape (JSON):**

{
  "head": { "vars": ["work", "celexNumber", "date"] },

**SPARQL patterns (confirmed against live endpoint):**

CELEX lookup:
```sparql
PREFIX cdm: <http://publications.europa.eu/ontology/cdm#>
SELECT ?work ?type ?date WHERE {
  ?work cdm:resource_legal_id_celex "32016R0679"^^xsd:string .
  ?work cdm:work_has_resource-type ?type .
  OPTIONAL { ?work cdm:work_date_document ?date . }
} LIMIT 5
```

Search by type + date:
```sparql
PREFIX cdm: <http://publications.europa.eu/ontology/cdm#>
SELECT ?work ?celexNumber ?type ?date WHERE {
  VALUES ?selectedType {
    <http://publications.europa.eu/resource/authority/resource-type/REG>
    <http://publications.europa.eu/resource/authority/resource-type/REG_ADOPT_INTERNATION>
    <http://publications.europa.eu/resource/authority/resource-type/REG_DEL>
    <http://publications.europa.eu/resource/authority/resource-type/REG_FINANC>
    <http://publications.europa.eu/resource/authority/resource-type/REG_IMPL>
  }
  ?work cdm:resource_legal_id_celex ?celexNumber .
  ?work cdm:work_has_resource-type ?selectedType .
  OPTIONAL { ?work cdm:work_has_resource-type ?type . }
  ?work cdm:work_date_document ?date .
  FILTER(?date >= "2023-01-01"^^xsd:date)
} ORDER BY DESC(?date) LIMIT 20 OFFSET 0
```

EuroVoc subject filter (correct predicate — NOT `work_is_about_subject_matter`):
```sparql
PREFIX cdm: <http://publications.europa.eu/ontology/cdm#>
SELECT ?work ?celexNumber WHERE {
  ?work cdm:resource_legal_id_celex ?celexNumber .
  ?work cdm:work_is_about_concept_eurovoc <http://eurovoc.europa.eu/2828> .
} LIMIT 20 OFFSET 0
```

EuroVoc concept search:
```sparql
PREFIX skos: <http://www.w3.org/2004/02/skos/core#>
SELECT ?concept ?label ?code WHERE {
  ?concept a skos:Concept .
  ?concept skos:prefLabel ?label .
  ?concept skos:notation ?code .
  FILTER(LANG(?label) = "en")
  FILTER(CONTAINS(LCASE(STR(?label)), "privacy"))
} LIMIT 20
```

Relation traversal:
```sparql
PREFIX cdm: <http://publications.europa.eu/ontology/cdm#>
SELECT ?relatedWork ?relatedCelex ?relationType WHERE {
  VALUES ?workUri { <http://publications.europa.eu/resource/cellar/3e485e15-...> }
  {
    ?relatedWork ?relationType ?workUri .
    ?relatedWork cdm:resource_legal_id_celex ?relatedCelex .
  } UNION {
    ?workUri ?relationType ?relatedWork .
    ?relatedWork cdm:resource_legal_id_celex ?relatedCelex .
  }
} LIMIT 50
```

### CELEX Number Format

| Sector | Domain | Type Examples | Example CELEX |
|:-------|:-------|:--------------|:--------------|
| `1` | Treaties | `CEE`, `UE` | `11957E` |
| `3` | Secondary legislation | `R` (Reg), `L` (Dir), `D` (Dec) | `32016R0679` |
| `5` | Preparatory acts | Various | `52016PC0467` |
| `6` | CJEU case law | court letter `C`/`T`/`F` + document letter: `J` (judgment), `O` (order), `C` (AG opinion), `P` (AG view), `A`/`B`/`N` (notices), … | `62024CJ0629` |
| `7` | National transposition measures | the transposed act's `{year}{type}{number}`, the notifying member state's ISO 3166-1 alpha-3 code (the 27 member states plus `GBR`), then `_` and the measure number | `72016L0680CZE_202505539` |

Format: `{sector}{year}{type}{number}` — e.g., `3` (sector) + `2016` (year) + `R` (regulation) + `0679` (serial) = `32016R0679` (GDPR). In sector 6 the type is two letters, the court (`C` Court of Justice, `T` General Court, `F` Civil Service Tribunal) then the document; the pairs in use are `CA CB CC CD CG CJ CN CO CP CS CT CU CV CX`, `TA TB TC TJ TN TO TT`, and `FA FB FJ FN FO`.

### CELLAR Content Negotiation

Act text is fetched from the EU Publications Office CELLAR resolver by content negotiation; the `eur-lex.europa.eu/legal-content` endpoint is now WAF-protected and no longer serves body text (issue #16).

- **URL**: `http://publications.europa.eu/resource/celex/{CELEX}` — format and language come from request headers, not the path
- **HTML**: `Accept: application/xhtml+xml` (OJ legislation) or `text/html` (CJEU judgments) → HTTP 200 with the act body; the HTML path tries both variants in order
- **Formex 4 XML**: `Accept: application/xml;type=fmx4` → HTTP 200 for a single-part act, or HTTP 300 (Multiple Choices) listing the sibling part streams, which are fetched and reassembled into one document; on HTTP 404, `Accept: application/zip;mtype=fmx4` → HTTP 200 with a zipped Formex package (redirected to `…/resource/cellar/{id}/zip`), whose manifest and the parts it names are reassembled the same way, or HTTP 404 when the work has no Formex at all (`31995L0046`)
- **Language**: `Accept-Language` requires an ISO 639-2/T three-letter code (`eng`, `fra`, `deu`, …); bibliographic 639-2/B codes (`ger`, `fre`) return HTTP 400. EUR-Lex two-letter codes are mapped before the request, and the fetch falls back to English when the requested language has no content
- **Bot-challenge guard**: a response carrying an AWS WAF challenge signature is refused and raised as `ServiceUnavailable`, never reported as available content
- Language codes accepted (mapped to ISO 639-2/T): `EN`, `FR`, `DE`, `ES`, `IT`, `PL`, `PT`, `NL`, `CS`, `DA`, `EL`, `ET`, `FI`, `HU`, `LT`, `LV`, `MT`, `RO`, `SK`, `SL`, `SV`, `BG`, `HR`, `GA`
